🔗 Step 2: Relational Joins with $lookup

MongoDB's $lookup performs left outer joins between collections, similar to SQL JOIN.

📌 Task 1: Customer Order History

db.customers.aggregate([ { $lookup: { from: "orders", localField: "_id", foreignField: "customerId", as: "customerOrders" }}, { $project: { _id: 0, name: 1, tier: 1, orderCount: { $size: "$customerOrders" }, totalSpent: { $sum: "$customerOrders.items.price" } }}, { $sort: { totalSpent: -1 } } ])
🔍 $lookup Breakdown:
  • from: Target collection to join
  • localField / foreignField: Matching fields (like ON clause)
  • as: Name of the new array field containing joined docs
  • $size & $sum: Calculate metrics from joined arrays

🔍 Step 3: Multi-Dimensional Analytics with $facet

$facet runs multiple aggregation pipelines in parallel on the same input, returning a single document with multiple analytical views.

📌 Task 2: CampusMart Dashboard Pipeline

db.orders.aggregate([ { $match: { status: "completed" } }, { $facet: { revenueByStatus: [ { $group: { _id: "$status", total: { $sum: "$items.price" } } } ], topProducts: [ { $unwind: "$items" }, { $group: { _id: "$items.product", orders: { $sum: 1 } } }, { $sort: { orders: -1 } }, { $limit: 3 } ], orderStats: [ { $group: { _id: null, avgItems: { $avg: { $size: "$items" } }, count: { $sum: 1 } } } ] }} ])
🔍 Why $facet?
  • Runs 3 independent analytics in ONE database pass
  • Ideal for dashboard widgets (revenue, top items, stats)
  • Reduces network round-trips and compute overhead
✅ Expected Structure:
{ "revenueByStatus": [ { "_id": "completed", "total": 280 } ], "topProducts": [ { "_id": "Keyboard", "orders": 1 }, ... ], "orderStats": [ { "_id": null, "avgItems": 1.33, "count": 3 } ] }

📐 Step 4: Schema Design for Analytics

Analytics workloads are read-heavy. Schema design should prioritize query performance over write normalization.

📊 Embedding vs. Referencing Decision Matrix

PatternBest ForAnalytics Impact
Embedding1-to-few, data accessed together✅ Fast reads, no joins, but limited by 16MB doc size
Referencing1-to-many, independent lifecycle⚠️ Requires $lookup, slower but scales infinitely
Computed FieldsFrequently filtered/sorted metrics✅ Pre-calculate totals/counts at write time
Bucket PatternTime-series / IoT data✅ Groups data by time window, reduces doc count
💡 Analytics Best Practice: Denormalize strategically! Store totalOrderValue, itemCount, and lastPurchaseDate directly in the customers document to avoid real-time $lookup during dashboard queries.

💾 Step 5: Materialized Views with $merge

Instead of running expensive aggregations repeatedly, save results to a dedicated analytics collection using $merge.

db.orders.aggregate([ { $match: { status: "completed" } }, { $group: { _id: "$customerId", totalSpent: { $sum: "$items.price" }, orderCount: { $sum: 1 }, lastOrder: { $max: "$date" } }}, { $merge: { into: "customer_analytics", on: "_id", whenMatched: "replace", whenNotMatched: "insert" }} ])
🔍 $merge Benefits:
  • Creates/updates customer_analytics automatically
  • whenMatched: "replace" → Keeps analytics fresh
  • Dashboard queries now run against a single collection (no joins)
  • Can be scheduled via cron or Atlas Triggers for real-time sync

🛠️ Troubleshooting & Tips

❌ "$lookup returns empty array"

Check field types! localField and foreignField must match exactly (String vs ObjectId is a common mismatch). Use db.collection.distinct("customerId") to verify data types.

❌ "$facet exceeds memory limit"

Add { allowDiskUse: true } to the aggregate options, or place $match before $facet to reduce input volume.

❌ "$merge fails with duplicate key"

Ensure the on field matches your _id structure. If merging into an existing collection, verify index uniqueness constraints don't conflict with your pipeline output.
